# Как устроен локальный Windows-overlay для транскрипции созвона и подсказок через Ollama

Я собрал Live Hints — открытое Windows-приложение, которое захватывает системный звук созвона, локально переводит русскую речь в текст и показывает подсказки в окне поверх других приложений.

Репозиторий: https://github.com/R0D10Nq/live-hints

Готовый выпуск: https://github.com/R0D10Nq/live-hints/releases/tag/v1.0.0

![Основной поток Live Hints](https://raw.githubusercontent.com/R0D10Nq/live-hints/main/docs/assets/live-hints-overview.png)

Главная цель проекта — не заменить собеседника или принять решение за пользователя, а дать локальный технический инструмент для сценариев, где нужно быстро удерживать контекст разговора: собеседования, переговоры, ежедневные созвоны и презентации.

## Зачем понадобилось отдельное приложение

У обычной связки «диктофон → облачное распознавание → чат с моделью» есть несколько практических проблем:

- звук и транскрипт уходят во внешние сервисы;
- между приложениями приходится переключаться;
- ответ появляется отдельно от окна созвона;
- трудно контролировать, что именно хранится и отправляется;
- задержка складывается из нескольких сетевых запросов.

В Live Hints рабочий путь построен вокруг локальных компонентов. Системный звук забирается через WASAPI loopback, распознавание выполняет `faster-whisper`, а подсказку генерирует локальная модель в Ollama. Electron отвечает за интерфейс и окно поверх приложений, Python — за STT- и LLM-сервисы.

## Архитектура

Поток данных выглядит так:

```text
Системный звук Windows
        |
        v
WASAPI loopback / микрофон
        |
        v
WebSocket STT-сервиса
        |
        v
faster-whisper на NVIDIA GPU
        |
        v
Транскрипт в Electron
        |
        v
HTTP-запрос и поток SSE
        |
        v
Ollama с локальной моделью
        |
        v
Подсказка в overlay-окне
```

Electron запускает локальные процессы, отслеживает их состояние и связывает renderer с системными возможностями через ограниченный IPC. STT-сервис принимает аудиофрагменты по WebSocket. LLM-сервис формирует запрос к Ollama и возвращает ответ потоком, поэтому интерфейс может показывать текст по мере генерации.

Рабочий LLM-путь в текущем выпуске только один — Ollama. В коде остались заготовки для других провайдеров, но я не заявляю их как готовую функцию, пока сервер действительно не умеет их маршрутизировать.

## Почему Windows и WASAPI

Задача проекта — слушать не только микрофон, но и звук собеседника из видеозвонка. В Windows это удобно делать через WASAPI loopback: приложение получает тот же аудиопоток, который выводится на выбранное устройство воспроизведения.

При необходимости можно включить второй канал с микрофона. Это полезно, когда в транскрипте нужен весь диалог, а не только удалённая сторона. Два источника увеличивают требования к обработке и требуют аккуратно разделять ошибки подключения, поэтому режим остаётся явной настройкой.

## Локальность без ложного обещания полного офлайна

Во время работы аудио, транскрипт и запрос к модели обрабатываются через сервисы на `localhost`. Однако полностью автономным приложение пока назвать нельзя:

- Python и зависимости устанавливаются отдельно;
- CUDA-компоненты должны подходить видеокарте и драйверу;
- Ollama и модели нужно загрузить заранее;
- portable-сборка содержит Electron-приложение, но не содержит весь Python-runtime, CUDA, Ollama и модели;
- установка зависимостей и загрузка моделей требуют сети.

Это важное ограничение. Формулировка «локальная обработка» здесь означает локальный рабочий контур после настройки окружения, а не отсутствие любых внешних загрузок.

## Реальная задержка

Изначальная цель проекта была агрессивной, но фактическую задержку нужно разделять по этапам. В локальных замерах текущая картина такая:

| Этап                          | Ориентир                                     |
| ----------------------------- | -------------------------------------------- |
| STT на совместимой NVIDIA GPU | около 300 мс для уже готового аудиофрагмента |
| Первый токен Ollama           | около 2–3 секунд                             |
| Полный ответ Ollama           | около 18–25 секунд                           |

Эти значения не являются SLA. Они меняются от модели, GPU, длины контекста и параметров генерации. Сквозные 500 мс нельзя честно обещать, пока основное время занимает LLM.

На практике полезнее быстро показать начало короткой структурированной подсказки, чем ждать полностью сформированный длинный ответ. Поэтому LLM-ответ передаётся через SSE и отображается потоком.

## Что сделано для безопасности

Проект не стоит считать завершённым продуктом для чувствительных переговоров, но несколько базовых границ уже проведены:

- Electron IPC ограничен явным списком каналов;
- локальные сервисы привязаны к `localhost`;
- загружаемые PDF, DOCX, TXT и MD передаются через ограниченный буферный обработчик;
- пользовательский контекст и история не входят в Git;
- чувствительные локальные файлы исключены через `.gitignore`;
- ошибки компонентов должны сопровождаться `trace_id` для корреляции;
- CodeQL проверяет JavaScript и Python;
- для сообщений об уязвимостях опубликована отдельная политика безопасности.

Выпускные EXE пока не подписаны коммерческим сертификатом, поэтому Windows SmartScreen может показать предупреждение. На странице выпуска лежит `SHA256SUMS.txt`, а README прямо описывает это ограничение.

## Как попробовать

Для текущего выпуска нужны:

- Windows 10 или Windows 11;
- Python 3.10 или новее;
- совместимая NVIDIA GPU с рабочим CUDA-путём;
- Ollama и загруженная текстовая модель;
- для анализа скриншотов — отдельная Vision-модель, например `llava:7b`.

Установщик, portable-файл и контрольные суммы опубликованы в выпуске v1.0.0:

https://github.com/R0D10Nq/live-hints/releases/tag/v1.0.0

Перед запуском стоит прочитать раздел требований в README. Текущий транскрайбер работает через `cuda` и `float16`; автоматического CPU-режима пока нет.
